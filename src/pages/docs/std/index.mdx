# The Velt standard library

The standard library is written in Velt and ships with the toolchain. A module is imported as
`velt/<module>`, the path of its folder in the standard library:

```ts
import { readFile, writeFile } from "velt/fs";
import { Deque } from "velt/collections";

await writeFile("notes.txt", "hello");
const queue = new Deque<string>();
queue.pushBack(await readFile("notes.txt"));
console.log(queue.length);
```

The [prelude](/docs/std/prelude/) (strings, arrays, `Map`, `Math`, `JSON`, `Error`, promises, …) is
in scope everywhere without an import, and so are Node's web globals: [`fetch`](/docs/std/net/http/),
`Request`, `Response`, `Headers`, `Blob`, `File`, `FormData`, `AbortController`, `AbortSignal`,
`URL`, `URLSearchParams`, `Set`, `RegExp`, [`Symbol`](/docs/std/prelude/symbol/), `TextEncoder`,
`TextDecoder`, `btoa`, `atob`, `DOMException`, `structuredClone`, `ArrayBuffer`, `DataView`,
`Uint8Array` and the other [typed arrays](/docs/std/prelude/typed_array/), and
[`ReadableStream`](/docs/std/io/streams/). `velt doc --std` generates HTML API documentation from
the sources; the [API pages](/docs/api/) here are generated the same way.

## Importing a module

- **An area or a module is a folder**, and its import path is that folder: `velt/fs`,
  `velt/net`, `velt/net/http`, `velt/encoding/json`. Each has one public API, the names its
  `index.velt` exports. The other files of a module are its internals, and importing one is an
  error that names the module to import instead:

  ```ts error
  import { Deque } from "velt/collections/deque";
  ```

  ```text
  error: `velt/collections/deque` is internal to `velt/collections`
    = note: import what you need from "velt/collections", the module's public API
  ```

- **The prelude is never imported.** Its names are in scope in every module;
  `import … from "velt/prelude"` is an error. The same goes for `velt/lang/…`, which implements
  the language: what a program uses of it is global (`Symbol`, `Proxy`, `Uint8Array`, …) or
  syntax (`import.meta`).

## Conventions

- **Errors** are thrown classes extending the prelude `Error { message }`. Catch them with
  `try { … } catch (e) { e.message }`; `e` is the union of the error classes the calls can
  throw, narrowed with `instanceof`. Each module has its own error class (`UrlError`,
  `CsvError`, …). Messages start with a capital letter (`Invalid URL: …`); `IoError` messages
  are lowercase, as in Node (`ENOENT: no such file or directory, open 'x'`, `handle is
  closed`). An error that escapes the program prints `Uncaught <Class>: <message> at
  <file>:<line>:<col>`, naming the error's actual class and, for an error thrown inside the
  standard library, the line of your code that called it.
- **Out-of-range arguments**: a mistake in the program (an index past an array's end, a digit
  count `toFixed` does not take, `repeat` with a negative count) panics, as an index out of
  bounds does. Positions that usually come from outside the program, such as offsets into a
  byte buffer read from a file or the network, throw a catchable `RangeError` where Node throws
  one, with Node's message, so a server can answer the request that sent them: `u8[]`'s
  `write`, `set` and `copy`, a typed array's `set` and `DataView`'s accessors. Such a method's
  error type includes `RangeError`.
- **I/O errors** are `IoError { code, message }` from [`velt/io`](/docs/std/io/). `code` is a
  Node-style name: `"ENOENT"`, `"EACCES"`, `"ECONNREFUSED"`, `"EOF"`, … A failed file-system
  call has Node's message: `ENOENT: no such file or directory, open 'data.txt'`.
- **Strings** are sequences of UTF-16 code units, as in JS: lengths and positions (`slice`,
  `indexOf`, regex match offsets, CSV and CLI column widths) count code units. Their text is
  stored and written as UTF-8; `Buffer.byteLength(s)` is that size.
- **Async functions return promises that start at once**, like JS (a direct `await` costs
  nothing). A promise that is neither awaited nor spawned is a compile error. `*Sync` variants
  block the calling thread.
- **Handles**: some modules return handle structs (`TcpStream`, `FileReader`, `ChildProcess`, …)
  that you can pass around and capture freely and release with `close()` (closing again does
  nothing). **Planned**: they become disposable classes with `using` support.

## Packages, not std

The standard library is the core every program can count on. Servers and database drivers are
libraries, so they are [packages](/docs/packages/), written on public std APIs only:
[http-server](/docs/packages/http-server/) (`serve`, with web-standard `Request` and `Response`
handlers), [sqlite](/docs/packages/sqlite/), [postgres](/docs/packages/postgres/) and
[redis](/docs/packages/redis/). A program imports a package by its name
(`import { serve } from "http-server"`) once `package.velt` lists it in `dependencies`. std keeps
what any of them builds on: `fetch` and the web types, [`velt/net/http/h2`](/docs/std/net/http/h2/),
[`velt/db`](/docs/std/db/), [`velt/dev`](/docs/std/dev/), [`velt/ffi`](/docs/std/ffi/) for
C libraries (and [`velt/native`](/docs/std/native/) for a Rust crate), and the
[WebSocket client](/docs/std/net/websocket/).

## Runtime-backed and pure modules

Every module is Velt source. Some bind runtime functions (`velt_rt_*`, implemented in Rust) for
what Velt can't do on its own:

| Module | Runtime use |
|---|---|
| `velt/fs`, `velt/net` | the file system, TCP and TLS streams (`connectTls` and `listenTls` through rustls; `startTls` is Velt) |
| `velt/net/http` | TCP and TLS connections, which the runtime pools between requests; HTTP/1.1, HTTP/2 (`velt/net/http/h2`) and body decoding (`velt/compress`) are Velt |
| `velt/net/websocket` | none of its own: the protocol is Velt on `velt/net` streams (the runtime only masks bytes, checks UTF-8 and draws masking keys) |
| `velt/process`, `velt/os` | arguments, environment, working directory, standard input, platform facts |
| `velt/process/child` | process spawning and pipes |
| `velt/net/udp`, `velt/net/dns` | sockets and the system resolver |
| `velt/sync`, `velt/task` | channel queues, abort signals and task groups |
| `velt/text` | Rust's `regex` engine; `escapeHtml` and `StringBuilder` are runtime passes over bytes |
| `velt/math` | arbitrary-precision integers (dashu-int) |
| `velt/crypto`, `velt/random/uuid` | only the operating system's secure random generator; hashing, HMAC, key exchange, ciphers and formatting are Velt (on the CPU's SHA and AES instructions through `velt/simd` where it has them) |
| `velt/random` | a per-thread wyrand generator |
| `velt/time` | only the local UTC offset; calendar math, parsing and formatting are Velt |
| `velt/hash` | FNV-1a over a string's or array's bytes, without a copy |

Pure Velt: `velt/path`, `velt/mem`, `velt/collections`, `velt/compress`, `velt/half`,
`velt/encoding` (with `velt/encoding/csv` and `velt/encoding/json`), `velt/cli`, `velt/jsx`, `velt/generate`,
`velt/net/http/h2`, `velt/net/url` and the timers of `velt/time` (built on `sleep`, `spawn` and
`velt/task` signals); some use only the runtime's UTF-8 conversions and error-code names.

## WebAssembly

On the WebAssembly targets the language and the pure modules work as on native targets, and
`velt/fs` uses the WASI file system. TCP, child processes and the native code of the database
packages are not available. On a JavaScript host (`wasm32-unknown-unknown`), `fetch` goes
through the host's own `fetch` ([On JavaScript hosts](/docs/std/net/http/#on-javascript-hosts)),
and [`velt/host`](/docs/std/host/) passes JS values to and from the host functions a program
declares; on `wasm32-wasip1`, `fetch` rejects with `IoError` `ENOTSUP` (no network)
([WebAssembly](/docs/tooling/webassembly/)).

# BTreeMap

`import { BTreeMap } from "velt/collections"`. A map with its keys kept in ascending order
(`K extends Comparable<K>`: numbers, strings, `bool`, and your types with a
[`compareTo`](/docs/reference/classes/#comparable)). It is a B+ tree: lookups, inserts and
deletes are O(log n), and ordered walks follow the linked leaves. Prefer it to
[`SortedMap`](/docs/std/collections/sorted_map/) once a map has more than a few hundred keys or
changes often: `SortedMap` shifts its arrays on every insert and delete.

```ts
import { BTreeMap } from "velt/collections";

const prices = new BTreeMap<i64, string>();
prices.set(300, "c");
prices.set(100, "a");
prices.set(200, "b");
console.log(prices.keys(), prices.first(), prices.last()); // [ 100, 200, 300 ] 100 300
console.log(prices.floorKey(250), prices.ceilingKey(250)); // 200 300
console.log(prices.range(100, 300)); // [ [ 100, 'a' ], [ 200, 'b' ] ]
for (const [price, name] of prices) {
  console.log(price, name);
}
```

## Operations

- `new BTreeMap<K, V>(entries?)`, `size`, `isEmpty()`, `clear()`.
- `set(k, v)`, `get(k): V | undefined`, `has(k)`, `delete(k): bool`. Like `Map`, the map shares
  the values it stores: `get` returns the stored object, not a copy.
- `getMany(keys): (V | undefined)[]`: `get` of each key, in order. The lookups of a batch run
  interleaved, each one's next node loading while the others search theirs, so in a map larger
  than the CPU's caches a batch costs about half as much as the same `get`s.
- `keys()`, `values()`, `entries(): [K, V][]`, all in key order; `for (const [k, v] of map)`
  walks the entries as they are when the loop starts.
- `forEach((v, k) => …)` visits the entries in key order. When the callback changes the map
  through another reference, the walk goes on from the first key after the one it visited last:
  keys added past it are visited, keys deleted before their turn are not.
- Ordered queries: `first()`, `last()`, `floorKey(k)` (the largest key `<= k`), `ceilingKey(k)`
  (the smallest key `>= k`), `undefined` when there is no such key, and `range(from, to)`, the
  entries with `from <= key < to`.

Keys are ordered by `compareTo`. For floats that is `<` with `NaN` after every other number and
equal to itself, so, as in `Map`, `NaN` is one key of its own (the last one), and `0` and `-0` are
one key.

A deleted key or value, or a replaced value, is released: the map keeps no reference to it, so a
string or an object is freed with its entry once nothing else holds it.

## Performance

A node holds up to 31 keys, and next to them a 64-byte line with two bytes of each key past the
prefix all of the node's keys share, which a search compares eight at a time with SIMD; it reads
a key only when those bytes tie. So a lookup reads about one cache line per level. A leaf keeps
its entries in the order they came, so an insert or a delete moves no other entry, and leaves
that fill up hand entries to a neighbor before they split, which keeps them about 85% full.

Numbers, `bool` and strings come with the byte encoding that search needs (`InlineKey`, below).
Keys of other types are compared in full, and get the fast search by implementing `InlineKey`. A
map of 1M `u64` keys and values takes about 27 MB, and string keys of up to 23 bytes are kept in
the map, not on the heap.

## Fast search for your own keys: `InlineKey`

`import { InlineKey } from "velt/collections"`. A key type gives the map its order-preserving
bytes: `hasInlineKey()` is `true`, and `inlineKey(offset)` returns bytes `offset .. offset + 8`
of an encoding that orders as the keys do (for keys `a < b`, `a`'s bytes are at most `b`'s in
byte order), as a big-endian `u64`, zero past its end. Numbers encode big-endian (signed ones
with the sign bit flipped), `bool` as one byte, and strings as their UTF-16 code units written as
UTF-8 would write them, which orders as `<` does; floats have no encoding yet. The other methods
(`inlineWord`, `inlineQuad`, `inlineWindow`, `inlineWide`) have defaults built on `inlineKey`.

Every other comparable type gets the default, `hasInlineKey()` `false`, and an
[`extend` block](/docs/reference/classes/#extend) for one type replaces it for that type:

```ts
import { BTreeMap, InlineKey } from "velt/collections";

struct OrderKey {
  customer: u32;
  order: u32;
}

// Ordered by customer, then order: the encoding is both fields' bytes, big-endian.
extend OrderKey implements Comparable<OrderKey>, InlineKey {
  compareTo(other: OrderKey): i64 {
    return this.customer != other.customer
      ? (this.customer as i64) - (other.customer as i64)
      : (this.order as i64) - (other.order as i64);
  }
  hasInlineKey(): bool {
    return true;
  }
  inlineKey(offset: usize): u64 {
    const both = ((this.customer as u64) << 32) | (this.order as u64);
    return offset >= 8 ? 0 : both << ((offset * 8) as u64);
  }
}

const orders = new BTreeMap<OrderKey, string>();
orders.set({ customer: 2, order: 1 }, "b1");
orders.set({ customer: 1, order: 7 }, "a7");
orders.set({ customer: 1, order: 3 }, "a3");
console.log(orders.values()); // [ 'a3', 'a7', 'b1' ]
console.log(orders.getMany([{ customer: 1, order: 7 }, { customer: 9, order: 9 }])); // [ 'a7', undefined ]
```

An encoding that does not order as `compareTo` does gives wrong answers, as a `compareTo` that is
not an order does.

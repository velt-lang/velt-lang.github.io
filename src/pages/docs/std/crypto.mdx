# velt/crypto

`import { sha256Hex, hmacSha256, randomBytes } from "velt/crypto"`. SHA-256 and SHA-1, HMAC,
secure randomness and constant-time comparison: what a program needs to sign and check tokens and
webhooks, store content by hash, or make session ids. And the building blocks of TLS 1.3: HKDF,
key exchange with X25519 and P-256, ECDSA signature verification on P-256, and the
ChaCha20-Poly1305 and AES-GCM ciphers. All of it is written in Velt; only the random bytes come
from the operating system.

```ts
import { sha256Hex, hmacSha256, randomBytes, randomInt, timingSafeEqual } from "velt/crypto";
import { utf8Encode, hexEncode } from "velt/encoding";

console.log(sha256Hex("abc")); // ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad
const mac = hmacSha256(utf8Encode("key"), utf8Encode("The quick brown fox jumps over the lazy dog"));
console.log(hexEncode(mac)); // f7bc83f430538424b13298e6aa6fb143ef4d59a14946175997479dbc2d1a3cd8
const die = randomInt(1, 7);
console.log(randomBytes(16).length, die >= 1 && die < 7, timingSafeEqual(mac, mac.clone())); // 16 true true
```

## Hashes and HMAC

- `sha256(data: u8[]): u8[]` (32 bytes) and `sha256Hex(s: string): string`, the lowercase hex
  digest of the UTF-8 bytes of `s`.
- `sha1(data)` (20 bytes) and `sha1Hex(s)`. SHA-1 is broken for collision resistance: use it only
  where a protocol requires it (the WebSocket handshake, git object ids).
- `hmacSha256(key, data)` and `hmacSha1(key, data)`: the HMAC as bytes. `hexEncode` and
  `base64Encode` from [velt/encoding](/docs/std/encoding/) turn bytes into text.

To check a signature, compare the bytes with `timingSafeEqual(a, b): bool`, which takes the same
time wherever the inputs differ, so an attacker cannot find a valid signature byte by byte from
response times. Inputs of different lengths return `false` at once (Node throws there):

```ts
import { hmacSha256, timingSafeEqual } from "velt/crypto";
import { hexDecode, utf8Encode } from "velt/encoding";

function verifyWebhook(secret: string, body: string, signatureHex: string): bool {
  const expected = hmacSha256(utf8Encode(secret), utf8Encode(body));
  return timingSafeEqual(expected, hexDecode(signatureHex));
}

const sig = "f7bc83f430538424b13298e6aa6fb143ef4d59a14946175997479dbc2d1a3cd8";
console.log(verifyWebhook("key", "The quick brown fox jumps over the lazy dog", sig)); // true
```

## Key derivation

HKDF (RFC 5869) with SHA-256 turns a shared secret into keys:

- `hkdfSha256(ikm, salt, info, length): u8[]`: `length` bytes derived from the input keying
  material `ikm`, with a `salt` (empty acts as 32 zero bytes) and a context string `info`.
- `hkdfExtractSha256(salt, ikm)`: the 32-byte pseudorandom key, and
  `hkdfExpandSha256(prk, info, length)`: the output from it. These are the two steps
  `hkdfSha256` runs, for protocols that use them apart (TLS 1.3's key schedule).
- The output is at most 8160 bytes (255 × 32); more throws `CryptoError`.

## Key exchange

- `x25519(scalar: u8[], u: u8[]): u8[]`: X25519 Diffie-Hellman (RFC 7748), the 32-byte shared
  secret of your 32-byte private scalar and the peer's 32-byte public key. The scalar is clamped
  as the RFC says. Throws `CryptoError` for a wrong length, or when the result is all zeros (a
  small-order peer point).
- `x25519PublicKey(scalar: u8[]): u8[]`: the public key to send for a private scalar. Any 32
  random bytes (`randomBytes(32)`) are a private scalar.
- `p256PrivateKey(): u8[]`: a new random P-256 private key, 32 big-endian bytes between 1 and
  n - 1.
- `p256PublicKey(privateKey: u8[]): u8[]`: its public key, uncompressed (0x04, x, y: 65 bytes).
  Throws `CryptoError` for a key that is not 32 bytes between 1 and n - 1.
- `p256Ecdh(privateKey: u8[], publicKey: u8[]): u8[]`: the ECDH shared secret (the
  x-coordinate, 32 bytes) with a peer's uncompressed public key. Throws `CryptoError` when the
  point is not on the curve, is compressed or has a coordinate not below p, and for a bad
  private key.

Never use a shared secret as a key directly: derive keys from it with HKDF.

```ts
import { ChaCha20Poly1305, hkdfSha256, randomBytes, timingSafeEqual, x25519, x25519PublicKey } from "velt/crypto";
import { utf8Encode } from "velt/encoding";

// Each side makes a private scalar and sends the other its public key.
const alice = randomBytes(32);
const bob = randomBytes(32);
const shared = x25519(alice, x25519PublicKey(bob));
console.log(timingSafeEqual(shared, x25519(bob, x25519PublicKey(alice)))); // true

const key = hkdfSha256(shared, [], utf8Encode("my-protocol v1"), 32);
const aead = new ChaCha20Poly1305(key);
const nonce = randomBytes(12); // never twice under one key
const sealed = aead.seal(nonce, utf8Encode("hello"));
const opened = aead.open(nonce, sealed); // null if it was tampered with
console.log(sealed.length, opened == null ? "tampered" : opened.utf8Slice()); // 21 hello
```

## Signatures

`p256Verify(publicKey: u8[], digest: u8[], signature: u8[]): bool` says whether `signature` is
a valid ECDSA signature on P-256 of `digest` by `publicKey`:

- `publicKey` is uncompressed (0x04, x, y: 65 bytes), as `p256PublicKey` returns it.
- `digest` is the hash of the message, which the caller computes: `sha256(message)` for ECDSA
  with SHA-256. A longer hash is cut to its leftmost 256 bits, as SEC 1 says.
- `signature` is DER (`SEQUENCE { r INTEGER, s INTEGER }`, what X.509, TLS and OpenSSL use),
  read strictly: BER variants are refused.
- It returns `false` for any malformed key or signature, and never throws.

import { p256Verify, sha256 } from "velt/crypto";

## Authenticated encryption

`new ChaCha20Poly1305(key)` (a 32-byte key, RFC 8439) and `new AesGcm(key)` (a 16- or 32-byte
key, NIST SP 800-38D) encrypt and authenticate. Both implement the `Aead` interface:

- `seal(nonce, plaintext, aad = [])`: the ciphertext with a 16-byte tag appended. The tag
  covers the associated data `aad` too, which is not encrypted.
- `open(nonce, sealed, aad = [])`: the plaintext, or `null` when the tag does not match (then
  nothing is decrypted).
- `sealInPlace(nonce, aad, buf, start, end)` encrypts `buf[start..end]` in place and writes the
  tag to `buf[end..end + 16]`. `openInPlace(nonce, aad, buf, start, end)` checks the tag at the
  end of `buf[start..end]` and decrypts the rest in place: `true`, or `false` with `buf`
  unchanged for a bad tag. Neither allocates, and both throw `CryptoError` for a range that
  doesn't fit `buf`.

Nonces are 12 bytes, and a nonce must never be used twice under one key: a counter, or 12
random bytes per message. A wrong key or nonce length throws `CryptoError`, and so does a
message longer than the cipher allows. A cipher object keeps scratch space between calls, so
two threads must not use one at once; tasks on one thread may share it.

## Randomness

- `randomBytes(n: usize): u8[]`: `n` bytes from the operating system's secure generator.
- `randomInt(min, max): i64`: uniform in `[min, max)`. Like Node, it throws `CryptoError` (with
  Node's message) when `min` or `max` is not a safe integer, `max <= min`, or `max - min` is 2^48
  or more.

For random numbers where security does not matter (simulations, shuffles, tests with a seed), use
[velt/random](/docs/std/random/); for ids, [`velt/random/uuid`](/docs/std/random/uuid/).

## Performance

Code that handles secrets runs in constant time: no branch, table index or loop depends on a key,
a nonce or the data. `x25519` and the P-256 functions take the same time for every private key;
`p256Verify` handles only public data and runs in variable time. AES-GCM uses the CPU's AES and
carry-less multiply instructions where it has them (AES-NI with PCLMULQDQ on x86-64, ARMv8 AES
with PMULL on arm64: [`u8x16.hasAes()`](/docs/std/simd/#aes-instructions)), and otherwise a
bitsliced AES with no table lookups, much slower; ChaCha20-Poly1305 needs no special
instructions.

The hashes are Velt code. In release builds on a CPU with SHA instructions (arm64, and x86-64 with
SHA-NI) they run on them through [velt/simd](/docs/std/simd/): on an Apple M4, 1.39 cycles per
byte for SHA-1 and 1.38 for SHA-256 (about 3 GB/s), as fast as Rust's `sha1` crate and faster
than `sha2`, also for one-block messages; HMAC with either is faster than Rust's `hmac`. Elsewhere
(other CPUs, WebAssembly, debug builds, or with `VELT_SIMD_DISABLE=sha`) they use portable rounds,
about 360 MB/s for SHA-256.

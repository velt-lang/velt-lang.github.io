# `package.velt`

Every package has a `package.velt` at its root: the manifest, written in Velt. `velt new` and
`velt init` write one.

<Callout title="Coming from 0.5">The manifest used to be `package.vlt`. It is no longer read: rename it to `package.velt` (the error says so), and your `.vlt` source files to `.velt`.</Callout>

```ts ignore
import type { Package } from "velt/package";

export const pkg: Package = {
  name: "hello",
  version: "0.1.0",
  velt: "0.1",                  // the velt versions that build it: the newest 0.1.x
  dependencies: {
    json: "1.2",                // registry package, semver requirement
    http: { version: "0.3" },   // object form
    util: { path: "../util" },  // local package (version optional)
    zstd: {                     // from a release archive, pinned by its SHA-256
      url: "https://github.com/acme/zstd/releases/download/v1.0.0/zstd-1.0.0.tar.gz",
      sha256: "<64 lowercase hex digits>",
      strip: 1,
    },
    "http-server": {            // from a git repository
      git: "https://github.com/velt-lang/velt",
      tag: "v0.6.0",
      path: "packages/http-server",
    },
  },
  paths: { "@app/*": "src/*" }, // import { x } from "@app/util"  →  src/util.velt (or .ts, .tsx)
};
```

The file is **data only**. `velt` reads it the way it would read JSON, without compiling or
running anything, so installing a package never runs its code. Besides the type import, it holds
one `export const pkg: Package = { … }` made of strings, numbers, `true`/`false`, arrays and
objects. Comments and trailing commas are fine; anything else (`null`, template literals,
variables, calls, spreads) is an error that points at it:

```text
package.velt:5:13: error: `null` is not allowed; leave the key out
```

In an editor, the language server ([`velt lsp`](/docs/tooling/editors/)) completes the fields valid where
you type, explains each on hover, and reports exactly the errors `velt` would, as you type. It
also asks the package's registry: it completes package names and versions in `dependencies`,
shows a dependency's newest and locked versions on hover, and flags requirements that no
published version matches or that leave out a newer one (with a fix). The
[`Package`](/docs/std/package/) type documents the same fields. Leave out the fields you don't
need. A key the manifest doesn't know is an error, with a
suggestion when it is close to one (`dependecies` → `dependencies`). `velt manifest` checks the
file and reports these errors without building anything.

## `name`, `version`, `description`, `keywords`, `entry`

- `name`: lowercase letters and digits, starting with a letter, with single `-` or `_` between
  words (`text-kit`, `text_kit`; not `text--kit`, `text_-kit` or `textkit-`). Names that differ
  only in `-` versus `_` count as the same in a registry. `velt` and `std` are reserved for the
  standard library (its modules are `velt/…`), as a package name and as a dependency's name
  (``the package name `velt` is reserved for the standard library``), and so are names whose
  first word is `rt`, `sig` or `native` (`rt`, `rt-str`) because a
  package's native functions are named `velt_<name>__…` and those prefixes are Velt's own
  (`velt_rt_…` is the runtime).
- A name can also be scoped, as on npm: `@scope/name`, each part lowercase words as above
  (`@sigx/server-renderer`). Registries hold unscoped packages only, so a package with a scoped
  name is a local (`path`) dependency of others, and can't have [`native`](#native) code yet.
- `version`: a semantic version.
- `description`: one line about the package, shown by `velt search` and registry listings: at most
  300 characters, no line breaks, no surrounding whitespace.
- `keywords`: search words, such as `["json", "parser"]`: at most 10, each lowercase letters,
  digits and `-` (at most 32 characters, starting with a letter or digit). `velt search` matches
  every word of its text against names, keywords and descriptions, names first.

  The registry keeps both per published version, so changing them means publishing a new
  version.
- `entry`: the program's root file, a path inside the package (default `"src/main.velt"`). A
  package with `src/main.velt` is runnable; a package with `src/lib.velt` is a library that other
  packages import. A package can have both. Without an `entry`, `src/main.ts` or
  `src/main.tsx` (`src/lib.ts`, `src/lib.tsx`) work like `src/main.velt` (`src/lib.velt`); two of
  them at once are an error.

## `velt`

The velt versions that build the package. `velt new` and `velt init` write the `major.minor` of
the velt that created the package (a pre-release writes its whole version, such as
`"0.2.0-rc.1"`), so installing a newer velt doesn't change how it builds: pre-1.0 minors may
change the language, and a toolchain's standard library and runtime belong to it.

The `velt` on your `PATH`, the launcher, runs the version the package's
[`velt.lock.json`](#veltlockjson) records when the field accepts it, so every machine builds a
commit with the same velt; otherwise (no lock yet, or `velt update`) the newest installed version
the field accepts, installing one first when none is
([`velt toolchain`](/docs/tooling/cli/#velt-toolchain)). A toolchain's
own `velt` started directly warns when its version is not one the field accepts:

```text
warning: package.velt asks for velt "0.2", but this is velt 0.1.0; it may not build the package
```

| `velt` | builds with |
|---|---|
| `"0.1"` | the newest installed `0.1.x` |
| `"0.1.3"` | `0.1.3` or a newer `0.1.x` |
| `"=0.1.3"` | exactly `0.1.3` |
| `">=0.1, <0.3"` | a requirement with an operator means what it means in `dependencies` |

"Builds with" is the choice when the package has no lock yet and on `velt update`; after that,
the version the lock records, while the field accepts it.

A version without an operator stays within its minor version, also after 1.0: `"1.2"` accepts
`1.2.5` but not `1.3.0`, unlike the same requirement in `dependencies`. A major version alone
(`"1"`) accepts any `1.x`. Pre-releases match only
a requirement that names one (`"0.2.0-rc.1"`). Leave the field out to build with any velt.
`velt manifest` and every other command check that the value is a requirement.

## `dependencies`

`import … from "json"` and `"json/sub"` resolve through `dependencies`: the dependency's
`src/lib.velt`, or `src/sub.velt` / `src/sub/index.velt` (or `.ts`, `.tsx`, tried like a relative
import's files). Standard library imports (`"velt/x"`)
and relative imports (`"./x"`) never do. Names that aren't identifiers are quoted
(`"my-lib": "1.0"`, `"@sigx/reactivity": { path: "../reactivity" }`; a scoped dependency needs
a `path`, `git` or `url`). `{ git: "https://…", branch: "main", path: "packages/x" }` takes the package
from a git repository ([git dependencies](/docs/tooling/packages/#git-dependencies)): a Velt package, or an
npm package (or a whole workspace of them) compiled from its TypeScript sources. The official packages (`sqlite`, `postgres`, `redis`, `http-server`) come this way or by
`path` ([official packages](/docs/tooling/packages/#official-packages)).
`{ url, sha256, strip?, path?, version? }` takes it from a release archive
([release archives](/docs/tooling/packages/#release-archives)):

- `url`: a `.tar.gz` or `.zip` at an `https` URL (the scheme in lowercase). Plain `http` is
  allowed only to this machine, and only in a manifest the project controls (its own, a workspace
  member's, a local path dependency's).
- `sha256`: the archive's SHA-256, 64 lowercase hex digits. Required: `velt add <url>` computes and
  writes it. Another archive at that URL is an error, not an update.
- `strip`: how many leading directories to remove (0 to 16), each the archive's only entry at its
  level, as `tar --strip-components` on a release's one top directory.
- `path`: the package's directory inside the archive.

Use a project's real release assets: a forge's generated archive of a tag can change its bytes.
For source, use `git` with a commit.

`velt add` edits this object and keeps your comments. In a member of a
[workspace](/docs/tooling/packages/#workspaces), `name: "workspace"` depends on another member, or on the
requirement the workspace writes for `name`. See
[Packages](/docs/tooling/packages/). A bare import that no dependency (and no `paths` alias) claims looks
for an [npm package](/docs/tooling/packages/#npm-packages).

## `paths`

Import aliases, like TypeScript's `compilerOptions.paths`, replace long `../../` chains:

- A bare specifier that matches a pattern resolves to the target, relative to the package root,
  before `dependencies` are consulted. `"velt/x"` and `"./x"` are never aliased.
- A pattern has at most one `*`, at its end, and so does its target (both or neither). The
  longest matching pattern wins. Each pattern has one target.
- Targets must stay inside the package (no `..`, not absolute).
- Each package's aliases apply to its own modules only.

## `jsx`

```ts ignore
jsx: { importSource: "sigx" },
```

The module whose `jsx-runtime` compiles the package's JSX: a dependency, `"velt/jsx"` (the
default), a `paths` alias, or `./dir` relative to the package root. A
`/** @jsxImportSource x */` comment at the top of a file wins ([JSX](/docs/std/jsx/)); Velt also
reads it from a `//` comment, `tsc` only from a block comment.

## `define`

```ts ignore
define: { __DEV__: "false", __SIGX_VERSION__: "\"1.0.1\"" },
```

Build-time constants, as Vite's `define`. Every reference to the name in the build's modules
(the package's, and those of the npm packages it compiles) that nothing in scope declares is
the literal, so `if (__DEV__) { … }` becomes `if (false) { … }` and the branch folds away, and
`{ __DEV__ }` is `{ __DEV__: false }`. A name the code declares keeps its own value, as with
esbuild's `define`: a parameter, a local, an import, a loop variable, a `catch` parameter or a
function or class of that name, in its scope. A property (`o.__DEV__`) and a type are left
alone too. Each value is the
*source* of a literal, as in Vite: `"true"`, `"false"`, `"null"`, a number (`"3"`), or a string
in quotes (`"\"1.0.1\""` or `"'1.0.1'"`); other expressions are an error. Only the root
package's `define` applies.

TypeScript code declares such constants in a declaration file, as sigx's `src/env.d.ts` does:

```ts ignore
declare const __DEV__: boolean;
```

Velt reads these ambient declarations (`declare const`, `let` and `var`, also inside
`declare global { … }`) from modules and from the `.d.ts` files of each package it compiles (in
the package's directory and below its `src/`). As in TypeScript, a declaration is global only
in `declare global` or in a file without imports and exports; in a module (such as an
`index.d.ts` with `export declare const version: string;`) it is the module's own. Velt has no
global variables, so a declared constant that a module refers to (without declaring the name
itself) needs a `define`; without one, the declaration is an error that says so. A `define` whose literal is not of the declared type (`boolean`, `string`, `number`)
is an error too.

## `native`

```ts ignore
native: {
  c: {
    c: { headers: ["<string.h>"] },
    sqlite3: { sources: ["native/sqlite3.c"], headers: ["native/sqlite3.h"], defines: { SQLITE_THREADSAFE: "1" } },
  },
  targets: ["x86_64-unknown-linux-gnu", "aarch64-apple-darwin", "x86_64-pc-windows-msvc"],
},
```

The package has native code: C libraries its Velt code calls with
[`declare c`](/docs/reference/c-interop/), or a Rust crate whose functions it declares
([Packages with native code](/docs/book/native-packages/)). A program that depends on it lists
it in [`allowNative`](#allownative).

- `c`: the C libraries the package's `declare c("<library>")` functions name, by that name. A
  package that declares C functions has this object; `c: { c: { headers: ["<stdlib.h>"] } }` is
  enough to call only the platform's C library, whose key is `c`. Each library is an object:
  - `system`: the platform's library, by build condition (`darwin`, `linux`, `win32`, `native`,
    `default`). `{ linux: "sqlite3" }` links `-lsqlite3` (`sqlite3.lib` on Windows), and
    `"framework:Accelerate"`, under `darwin` only, a macOS framework. The first condition the
    build has applies; on a target none applies to, the library's declarations are errors. A
    value is a library's name, at most 64 bytes, not a linker flag or a file name (`libm.so.6` is
    an error naming `m`). The `c` library has no `system`.
  - `headers`: the C headers the declarations are checked against, one list for every target: a
    path in the package (`"native/sqlite3.h"`), or `"<string.h>"` for a C library header. Names
    are letters, digits, `_`, `-`, `+` and `.`, in `/`-separated segments that aren't `.` or `..`
    and don't start with `-`; a path outside the package, an absolute path in angle brackets or an
    empty segment is an error. Other libraries' headers aren't found by name (`"<sqlite3.h>"`):
    the package ships its copy.
  - `unchecked: true`: the library has no headers (a binary-only SDK), so its declarations go
    unchecked; `allowNative`'s refusal and `velt check` say so. Every library the package declares
    functions of lists `headers` or says `unchecked`, not both.
  - `sources`: the library's `.c` files under `native/` (`"native/sqlite3.c"`), which
    `velt native build` compiles for each target with the pinned zig. A library has `sources` or
    `system`, not both. A package with `sources` ships all of `native/`.
  - `defines`: what its `sources` and headers are compiled with: `{ SQLITE_THREADSAFE: "1" }` is
    `-DSQLITE_THREADSAFE=1`.
- `targets`: the targets `velt publish` builds or takes a prebuilt library for, of the C
  `sources` or of a Rust crate (it fails if one is missing): `x86_64-unknown-linux-gnu`,
  `aarch64-unknown-linux-gnu`, `x86_64-apple-darwin`, `aarch64-apple-darwin`,
  `x86_64-pc-windows-msvc`, `aarch64-pc-windows-msvc`.
- `path`: a Rust crate's directory, a directory name in the package root (default `"native"`). A
  package with `targets` and no `c` sources has a Rust crate there (a `cdylib` + `staticlib` built
  on the `velt_native` crate).
- `wasm`: must be `false` (the default); native libraries are not supported on WebAssembly.

## `allowNative`

```ts ignore
allowNative: [
  "sqlite",                                                                // the registry, or a local path
  { name: "llama", git: "https://github.com/o/llama" },                   // that repository, any commit
  { name: "duck", url: "https://github.com/o/duck/releases/download/" },  // archives under that prefix
],
```

The packages with native code (C libraries or a Rust crate) the program allows. Native code runs
with no safety net, so a program says which packages it trusts with it: installing or building
with any other package that has native code, anywhere among its dependencies, is an error that
names the chain of dependencies and the line to add.

```text
package `sqlite` (through `orm` → `sqlite`) has native code, which runs with no safety net
allow it in package.velt, if you trust it: allowNative: ["sqlite"]
```

- Only the root package's list applies. At a [workspace](/docs/tooling/packages/#workspaces)'s
  root, `velt install` checks each member's list before it builds anything.
- A name allows that package from the registry or a local path. A package from git needs
  `{ name, git }`, and one from a release archive `{ name, url }`, with exactly one of the two.
- `git` matches the repository at any commit. URLs compare without a trailing `/` or `.git`, with
  the host in any case and a default port dropped, and `user@host:/path` as
  `ssh://user@host/path`. A home-relative `git@host:path` and `ssh://git@host/path` are different
  repositories: write the entry the way the dependency spells it (the error names both URLs).
- `url` is an `https` prefix with a path under the host, and matches whole path segments:
  `https://github.com/o/duck/releases/download/` allows every release of that project. A refusal
  suggests the archive URL's directory as the prefix (and nothing for a URL no prefix can name,
  such as plain `http`). An archive cached from one URL counts for another only once that URL has
  served the same bytes.
- One package name has one source. The root's own dependency entry for a name wins over what
  other packages ask for (`velt install` prints a note, and the lock records it); two
  dependencies that ask for one package from different sources, when the root doesn't name it,
  are an error.
- A refusal says when a package's C library is `unchecked`:
  ``its C library `sdk` is not checked against headers (`unchecked: true`)``.
- `velt add` and `velt remove` keep `allowNative` and `native` when they rewrite the file.
  `velt add` of a package with native code fails until the list names it, printing the line to
  add. `velt install` and `velt update` print a note when a package's native code changes.

When `velt check` passes, it ends with what the list allows: each package's C libraries, whether
it has a Rust crate, and each piece of its unsafe code by file and line
([what a program trusts](/docs/tooling/packages/#what-a-program-trusts)).

<Callout title="Coming from 0.5">A program that uses `sqlite` or `postgres` lists it here: `allowNative: ["sqlite"]`. Then run `velt install` once, since `velt.lock.json` records the list. `redis` has no native code and needs no entry.</Callout>

## `build`

```ts ignore
build: { cpu: "x86-64-v3" },
```

How the package's program is built. Only the root package's applies.

- `cpu`: the CPU the program is built for, as `velt build --cpu`: `"baseline"`, `"x86-64-v2"`
  (the default on x86_64), `"x86-64-v3"`, `"x86-64-v4"`, `"native"` or a CPU name such as
  `"znver4"` ([CPU](/docs/tooling/platforms/#cpu)). `--cpu` and `VELT_CPU` take precedence, and a CPU of
  another architecture does not apply to a build for this one (`"x86-64-v3"` leaves arm64
  builds at their default, `"neoverse-n1"` x86_64 builds at x86-64-v2).

## `tsCompat`

```ts ignore
tsCompat: ["src/components", "src/models"],
```

Folders whose modules a TypeScript client shares, so they must stay in the
common subset of TypeScript and Velt (like the
client's `tsconfig.json` `include`). `velt check --ts-compat` without paths lints every `.velt`,
`.ts` and `.tsx` file in them ([`velt check`](/docs/tooling/cli/#code-shared-with-typescript---ts-compat)),
and the editor shows the findings, with their fixes, as you type
([editors](/docs/tooling/editors/#code-shared-with-typescript)). Nothing else changes: `velt build` and a
plain `velt check` never lint.

- Each entry is a `/`-separated path relative to the package root (`src/models`; not
  `./src/models`, `../shared` or `/abs`, no trailing `/`).
- Each folder once: a folder listed twice, or inside another listed one, is an error. Case
  doesn't matter here (`src/models` and `src/Models/sub` overlap): on macOS and Windows they
  are the same folder, so such a list would mean something else on Linux.
- The files in a folder are found as `velt check` finds a package's: `node_modules/`,
  `target/`, hidden and symlinked directories are skipped, and so is a package nested in the
  folder (a directory with its own `package.velt`), which lints its own `tsCompat`.
- Not empty: leave the field out instead of writing `[]`.
- A folder that doesn't exist is a warning in the editor and an error for
  `velt check --ts-compat`.

## `registry`

```ts ignore
registry: "https://registry.example.com",
```

A root package's `registry` URL, or `VELT_REGISTRY` set to an `http(s)://` URL (which takes
precedence), replaces the local registry directory for `velt add`, `velt install` and
`velt publish` ([Registries](/docs/tooling/packages/#registries)).

## Other tools

`velt manifest --json` prints the validated manifest as JSON, with the defaults filled in, for
tools that can't read Velt:

```text
$ velt manifest --json
{
  "dependencies": {
    "json": "1.2"
  },
  "entry": "src/main.velt",
  "name": "hello",
  "paths": {},
  "velt": "0.1",
  "version": "0.1.0"
}
```

## `velt.lock.json`

`velt install` writes `velt.lock.json`, which pins the exact version and content hash of every
dependency. It is generated JSON, pretty-printed with a stable key order so diffs stay readable:
`"version": 1` and a `"packages"` array with one entry per package (`name`, `version`, `source`:
`"registry"`, `"path+<relative path>"`, `"git+<url>?branch=main&path=<dir>#<commit>"` ([git dependencies](/docs/tooling/packages/#git-dependencies)),
`"url+<url>?strip=1&path=<dir>#sha256:<hex>"` ([release archives](/docs/tooling/packages/#release-archives)) or,
in a [workspace](/docs/tooling/packages/#workspaces), `"workspace+<member dir>"`, `checksum`, `dependencies`, and for a package with
native code a `"native"` object with the checksum of its prebuilt library for every published
target). It also records the root's [`allowNative`](#allownative) list, sorted
(`"allowNative": ["sqlite"]`), so a change of what the program trusts shows in the lockfile's
diff, and as `overrides` the dependencies whose source the root's own entry chose. A workspace's
lockfile has no list. In a package with a [`velt` field](#velt), it also records the velt version that builds the
package, `"velt": "0.2.1"`: the one that created the lock, kept until `velt update` (or until
the field doesn't accept it). The `velt` on your `PATH` runs that version in the package, installing it
if needed, so a laptop and CI build a commit with the same compiler even when newer patch
versions are installed. Commit it for applications. `--locked` on `build`, `run`, `test` and
`install` fails instead of changing it, and fails when a different velt runs than the lock
records or when its `allowNative` list doesn't match `package.velt`'s (run `velt install` once).
